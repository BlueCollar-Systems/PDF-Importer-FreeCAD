# Draft drawing-page contract v1

This development-only proposal separates drawing facts from reader interpretations and product decisions. It is outside the addon runtime; no production reader, parser, geometry pipeline or writer adopts this draft yet. All fixtures are wholly invented, with explicitly dummy SHA strings and fixture:// locators. No customer PDF or extracted customer data belongs in this directory. Authored expectations are not executed proof; test outcomes are reported separately in CI and development receipts.

The draft schema is docs/contracts/drawing-page-contract-v1.schema.json. Fictional cases are in tests/fixtures/drawing-page-contract-v1/. The test-only consistency reference is tests/test_drawing_page_contract.py; it reads JSON and performs no file mutation or PDF parsing. Install development requirements, then run that test through the existing test suite or directly with python -I -B tests/test_drawing_page_contract.py. Workspace-specific admission rules still apply to local runs.
## Separate identities and facts

`content` identifies bytes by SHA256 and byte length, with the reader-reported page count. An occurrence is a separate local file/locator observation: identical bytes may have several occurrence IDs and locations. Do not deduplicate occurrences merely because their content hashes agree. The schema stores facts; it does not grant file access or mutation authority. A page fact is keyed by (content.sha256, page_index), independently of an occurrence locator. All three content-SHA slots require exactly 64 lowercase hexadecimal characters, with no trailing whitespace.

An `interpretation` binds its ID to source content SHA, reader/build, exact JSON options, reader-output schema version and this contract version. A reader/build/options/content/schema or interpreted page-fact change needs a new interpretation ID. Options remain opaque JSON; this seed does not specify canonical option serialization or invent an interoperable options hash. A mismatched source content SHA is stale, even if page fields look useful.

Each page index is 1-based. `kinds.values` may contain both `drawing` and `bill_of_materials`: a mixed page is not automatically an ambiguous page. A classification state other than `identified` carries no asserted kind values in this minimum seed. Ambiguous page-kind candidate values are not represented in v1; retain the ambiguous state with an empty values array. `read_quality=text_available` describes usable reader text, not visual correctness. It can coexist with unrecognized kinds/fields. `no_extractable_text`, `read_error`, `unsupported`, `unknown` and `not_evaluated` remain different states.

Every governed field has an explicit state: `present`, `missing`, `unknown`, `ambiguous`, `unsupported`, or `not_evaluated`. Missing means this interpretation reports the field absent; unknown means it cannot determine a value; not_evaluated means no evaluation occurred. Neither no-text nor read-error alone proves a printed field absent. The five roles are job_name, job_number, drawing_number, main_mark and revision. Literal strings retain case, punctuation, spacing and leading zeros. `M7` differs from `m7`; `AB-0042-a` differs from `AB-0042-A`. The contract defines no lossy normalized identity key. A reader label such as unclear maps to unknown; unclear is not an additional v1 state.

Present fields carry one `literal`, including an explicitly observed empty string, and at least one evidence item. Revision missing, revision `""`, and revision `"0"` are different. Numeric 0 is not the string `"0"`. Ambiguous fields carry at least two distinct literal alternatives and at least two evidence items. Every claimed alternative must have supporting evidence with exactly the same literal and governed field role; array length alone is insufficient. Every evidence item under a governed field must match that field role, in every state; differently assigned observations belong in other_evidence. Present evidence must support its exact literal, and ambiguous evidence must support one of its alternatives. Missing and not_evaluated require empty evidence arrays. Unknown and unsupported may retain role-matched raw observations without a literal, alternatives or promotion to an established value. Evidence names the claimed role, literal label/value, origin, method and context. A DWG NO observation or BOM item never establishes a main mark by itself. Unassigned BOM evidence may remain in `other_evidence` without promotion.

`rule_decisions` are separately versioned records, bound to interpretation ID and a rule ID/version. `proposal_ready` is a rule result, not permission to rename, publish, fabricate or write. Human reviews are also bound to a specific interpretation ID and scope. Each scope is interpretation-wide: a confirmed `field_literals` review covers the governed fields on every page of that interpretation. It must not represent inspection of only one page or field. Narrower review targets are unsupported in this draft; retain `needs_review` until the whole scope has been reviewed, or define targeted reviews in a separately versioned extension. An old review cannot silently approve a new reader/options/source interpretation. A confirmed topic review grants no fabrication or file-write authority. This seed does not define actual reviewer authentication or fabrication approval.

## Minimum semantic checks beyond JSON Schema

The JSON Schema checks shape, states and value types. The following cross-record semantics require checks beyond the schema. The development-only test reference exercises them against fictional records; no production adapter implements them in this pilot:

- Every occurrence content SHA equals `content.sha256`; occurrence IDs are unique.
- Interpretation source SHA matches the content it describes. Page indices are unique and within 1..page_count.
- `interpretation.coverage=complete` requires exactly one page for every integer index from 1 through `content.page_count`, with no duplicate or out-of-range indices. Every page must also have `read_quality != not_evaluated`, `kinds.state != not_evaluated`, and no governed field whose `state` is `not_evaluated`. An evaluated `unknown`, `read_error`, `no_extractable_text` or `unsupported` result can account for a page without establishing a known field value or successful reading. Partial coverage is explicit; stale and partial are different. Coverage alone does not establish rule readiness.
- Present literal evidence agrees exactly with its value and role; ambiguous alternatives remain distinct literal strings. No main-mark inference from a drawing number or BOM item.
- Decision and human-review interpretation IDs match the interpretation. No proposal_ready based on stale or incomplete facts in the fictional name-proposal fixture policy.

The illustrative `fictional-name-proposal` rule v0.1 is fixture-only, not a shared production acceptance threshold. It reports case-distinct marks/jobs, missing or ambiguous main marks, and read-quality/coverage review reasons. Other future rule sets can decide differently while preserving the same facts and interpretation binding.

## Optional operation protocol stays separate

`optional-operation-examples.json` is a vocabulary sketch, outside the page schema. Planned, committed, interrupted and unresolved are distinct. Planned is intent; interrupted/unresolved require reconciliation and never imply success. A committed claim requires content/size/exact-destination verification, with independent real receipts in any future implementation. Even a committed record is an observation claim, not authorization. This seed implements no writer, journal, undo, recovery, lock protocol or release gate.

## R2 scope and identity clarifications

Known kinds additionally include `letter` and `printed_tag_sheet`. These describe purpose, independent of read quality. A scan/no-text state is not a page kind. Naming a kind does not prove usable text, visual correctness or successful parsing; the fictional printed-tag-sheet case retains no_extractable_text and unknown fields.

Evidence cardinality is only a shape check. Semantic validation requires exact role/literal coverage for present fields and every ambiguous alternative, including empty-string evidence for a claimed empty literal. No support means no established value. Added negatives distinguish zero support, an unsupported alternative and a wrong evidence role.

`fixtures-interpretation-pairs.json` has nine compact two-record scenarios. Materialize each right record by its listed replace-only JSON paths from the invented baseline; this is an in-memory fixture convention, not a writer. The immutable interpretation payload is `content` plus `interpretation` except `id` plus `pages`; occurrences, decisions and reviews are excluded. Compare JSON structurally: object key order is ignored and list order is retained. Booleans, strings, null and numbers are separate JSON kinds. Numbers compare by exact mathematical decimal value rather than token spelling: `1`, `1.0` and `1e0` are equal, while `0.1` and `0.10000000000000001` remain distinct. Finite values below binary-float range remain distinct from zero. The test-only JSON loader preserves decimal digits with Decimal and keeps its existing overflow rejection; equality performs no rounding through a Decimal arithmetic context. Metadata byte_length is a mathematical integer from 0 through 9007199254740991; page_count and page_index are mathematical integers from 1 through that same bound. Whole-valued numeric spellings such as 1.0 are integers; booleans and fractions are not. These limits do not cap opaque option numbers. JavaScript consumers need lossless numeric parsing and exact value comparison before binding an interpretation; a consumer unable to represent a numeric input losslessly must reject it as unsupported before binding, not silently round it through Number or JSON.parse. This includes metadata: validate its original numeric token losslessly before integer and range checks, since a near-bound fractional token can round to an apparently safe integer in binary floating point. This is not canonical serialization, a production options hash or an ID-minting algorithm. Reader/build/options/output-schema/content/page-fact changes under the same ID conflict. A new ID may identify a valid replacement from a different reader; the fictional reader/build names are not an allowlist. New interpretations rebind rule decisions and cannot carry old human reviews. ID minting/canonical option hashing remains undecided.

Both root and interpretation page-contract versions must be supported and equal; unknown or mismatched versions and unknown separately versioned rule-decision formats fail this draft. The loader boundary must fail closed on duplicate JSON keys and non-finite numbers, including an overflowing exponent; JSON Schema alone does not enforce those token-level conditions. Reader_output_schema_version is an immutable reader-identity component, not a production compatibility allowlist. Unsupported future page contracts require an explicit outer adapter disposition, never silent reinterpretation as this draft.

Coordinates, bounding boxes and page rotation are omitted from minimum v1. A future evidence-locator extension needs separately reviewed coordinate/rotation semantics. Unknown page count and file-level open/read errors belong in an outer file/error envelope, outside this page contract. This contract requires an asserted positive page count and never fabricates pages for unreadable files. No outer envelope is implemented here.

Actual production document values, evidence and locators are `local_only`. Public/repository fixtures remain wholly invented and label all content SHA strings dummy. This is an adapter data-handling rule, not an enforcement mechanism or permission to publish production records.

Additional codes: MAIN_MARK_UNKNOWN; PRESENT_EVIDENCE_REQUIRED; AMBIGUOUS_EVIDENCE_REQUIRED; AMBIGUOUS_ALTERNATIVE_UNSUPPORTED; UNKNOWN_FORMAT_VERSION; UNKNOWN_INTERPRETATION_CONTRACT_VERSION; UNKNOWN_RULE_DECISION_VERSION; INTERPRETATION_IDENTITY_UNCHANGED; IMMUTABLE_INTERPRETATION_ID_CONFLICT; NEW_INTERPRETATION_ID; OLD_HUMAN_REVIEW_NOT_APPLICABLE. Invalid records yield no usable rule decision or parser result merely because a decision field exists.

The separate operation sketch binds bound_content_fixture_id, bound_content_sha256 and expected_byte_length to the referenced positive fixture content. A fictional committed expectation is complete only when verified observed SHA, byte length and exact destination match those expectations and state is committed. The fifth case has a mismatched observed byte length and is incomplete. These are authored fictional expectations, never executed proofs or write authorization. OP_COMMITTED_BOUND_PROOF_MATCH and OP_EXPECTED_BYTE_LENGTH_MISMATCH distinguish the pair. Expected and observed optional-operation byte lengths use the same bounded mathematical-integer policy as content.byte_length, including whole-valued decimal spellings and exclusion of booleans, fractions and values above 9007199254740991. This tightens only the test reference predicates; the operation sketch and its fictional records are unchanged.

## Open coordination decisions

1. This FreeCAD repository is the proposed canonical home for the draft schema/docs/fictional fixtures, outside the runtime. Existing pdfcadcore host sync rules and reviewed variants remain unchanged. Tag JavaScript and SketchUp consumers need their own adapters and version agreement; this draft moves no Python core into them.
2. How should adapters mint stable occurrence/interpretation IDs, including rename/hard-link observations and future canonical JSON option hashing? No cross-platform identity algorithm is assumed here.
3. Which independently versioned product rules consume these facts, and which review scopes are required for their proposals? Do not turn this schema into a universal writer or fabrication authorization policy.

This pilot changes only draft documentation, fictional fixtures, development tests and their test dependency. Existing importer qualification, guarded native checks and release coordination remain separate work.
